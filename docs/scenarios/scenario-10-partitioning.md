# Сценарий 10. Партиционирование

## Задача

Разделить таблицу `files` на физические части по году `created_at_utc`.

Это должно помогать запросам, которые выбирают конкретный период: прежде всего
сценарию 5 и отчёту из сценария 7.

## Моя логика

Таблица `files` остаётся одной таблицей для SQL и C#.

PostgreSQL хранит её строки в партициях `files_2025`, `files_2026`, `files_2027`.

При добавлении файла PostgreSQL смотрит на `created_at_utc` и кладёт строку
только в одну подходящую партицию.

При запросе за 2026 год PostgreSQL может не читать партиции за 2025 и 2027.

## Граничные случаи

Для дат, для которых ещё нет отдельной годовой партиции, есть `files_other_dates`.

Перед новым годом нужно создать отдельную партицию для него.

## Индексы/производительность

Партиционирование полезно только когда в запросе есть условие по `created_at_utc`.

Для поиска по папке или по содержимому файла оно само по себе не даёт выигрыша.

## SQL прямо в C#: raw string literal и FormattableString

В `ReadPartitionRowsAsync` запрос записан через `FormattableString sql = $"""..."""`:
raw string literal сохраняет читаемый многострочный SQL, а `FormattableString`
хранит шаблон отдельно от значений `{start}` и `{end}`.

Перегрузка `QueryAsync` в `SqlExecutorExtensions` заменяет эти места на `@p0`
и `@p1`, а значения передаёт через `NpgsqlParameter`. Значения не становятся
частью текста SQL. Интерполяция здесь предназначена только для значений,
не для имён таблиц, колонок или SQL-фрагментов.

Тип `FormattableString` указан явно: с `var` или `string` получилась бы уже
готовая строка со вставленными значениями. Файл `scenario-10-partitioning.sql`
остаётся шаблоном для пункта меню «показать SQL».
